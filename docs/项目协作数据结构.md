# 项目协作数据结构

Electron Manager 使用 Markdown 作为项目协作的主数据源。JSON 只保存配置和可重新生成的索引，不承担人工维护的业务事实。

## 当前结构

```text
<manager-data-root>/projects/<project-id>/
  project.json
  agent-brief.json
  index.json
  record-counters.json
  versions/
    版本索引.md
    V001/
      工程任务.md
      想法与问题.md
      研究.md
      待确认事项.md
      风险与后续.md
      工作记录/
        YYYY-MM.md
  collaboration/
    当前项目基线.md
    数据层规范.md
    Agent 同步交接.md
    需求变更索引.md
  constraints/
    项目约束.md
  documents/
  skills/
    project-collaboration/
      SKILL.md
```

## 版本边界

- `versions/Vxxx/` 是任务、想法、研究、协作问题、风险和工作记录的物理边界。
- 当前版本由 `project.json.currentVersionId` 指定。
- `agent-brief.json.currentDataPaths` 给出当前版本的准确写入路径。
- 已完成版本默认只读；只有追溯历史或当前上下文不足时才读取。
- 文档和项目约束属于项目整体，`version:: Vxxx` 只表示来源，不参与版本筛选。

## 协作记录

- 任务使用 `Txxx`，是执行和验收的基本单位，并在执行前声明 `work_level:: light | standard | deep`。
- 想法使用 `Ixxx`，处理后必须写明回答、关联任务或不处理原因。
- 研究使用 `Dxxx`，以 `mode:: breadth | depth` 区分广度和深度，以 `status:: pending | doing | done | archived` 表示生命周期。
- 协作线程使用稳定 `Qxxx`，保存用户与 Agent 的连续对话和下一步责任。
- 风险使用 `Rxxx`，保存验证限制、技术风险和后续工作，不进入双向协作线程。
- 工作记录使用 `Lxxx`，按版本和月份保存；只要修改源码、配置、测试、项目文档、知识条目或协作规则等交付文件，就必须记录。
- 工作记录使用 `record_level:: light | standard | deep`，并与关联任务最终的 `work_level` 一致；所有文件修改仍必须记录。

工作等级边界：

- `light`：单一、局部、易回退，不改变架构、数据结构、公开接口、权限或安全边界。
- `standard`：一个方案明确的常规功能或缺陷修复，包含多个相关步骤或组件，但风险可控。
- `deep`：架构、数据或协议迁移、跨系统契约、权限与安全边界、不可逆操作，或必须记录取舍的高影响方案。
- deep 任务必须写 `depth_reason:: architecture | migration | cross_system | security | irreversible | decision`，并保留“关键约束”和“方案与回退”；文件多、步骤多或耗时长本身不构成 deep。
- `depth_reason` 只写一个主原因，优先选择直接决定验收和回退方式的原因：权限/信任边界用 `security`，数据或版本化协议兼容用 `migration`，不可逆操作用 `irreversible`，其次才是 `architecture`、`cross_system`、`decision`；其他条件写入关键约束。
- 跨系统指独立部署、版本或责任边界。同一应用内能够随同一版本原子升级、无需新旧端共存的普通模块/IPC 调整仍是 standard；需要独立升级或新旧端共存时才属于协议迁移。
- 命中更高等级条件时使用更高等级；任务范围扩大时，先更新 `work_level`。
- 简单明确的 light 工作直接执行；standard、deep 或范围不明确的工作先建立简洁可执行的当前计划，并在执行中按证据动态调整。
- 用户目标和验收是稳定锚点，执行计划只是可替换的工作状态。不得静默改变目标；目标需要变化、不可行或与新约束冲突时回到用户确认。
- 指令冲突按“运行时安全边界 > 用户当前明确目标与确认 > 任务验收和任务约束 > 当前项目约束 > 协作记录规则 > 计划、并行和子 Agent 启发式策略”处理。
- 不保存无价值的计划演变；协作数据只保留当前有效范围、实际关键判断、结果和验证，中间尝试仅在形成高影响决策、风险或后续事项时记录。
- 以整体完成效率为优先。环境支持子 Agent 时，可委派边界清楚、彼此独立、可并行或适合专项调查的工作；简单顺序工作或协调成本高于收益时不拆分，主 Agent 保留目标、验收、依赖协调、结果整合和最终验证责任。
- 同一目标、版本、功能区域和验收轮次中的连续 light 修改允许合并；无关目标以及需要独立排期、验收、发布或风险跟踪的工作不得合并。
- 无需排期和后续跟踪的即时 light 修改可不创建任务卡，使用 `task_short_id:: T000` 写一条 light 日志。
- priority 仅表示紧急程度，与工作等级无关；`high` 只用于当前阻塞、安全或数据损坏、发布关键问题。

问题状态固定为：

- `open`：待用户回复。
- `decided`：待 Agent 回复或落实。
- `resolved`：线程已完成。
- `expired`：仅由 Agent 或系统归档已被替代、确实无关的线程，不作为用户日常操作。

每条用户或 Agent 回复都追加到问题的 `### 对话记录`，不覆盖历史消息。用户新建线程或回复后，状态进入 `decided`；Agent 追问时进入 `open`；确认协作完成后进入 `resolved`。已完成或归档的线程仍可继续讨论，新的用户回复会重新进入 `decided`。

风险状态固定为：

- `open`：仍需关注。
- `resolved`：已处理。
- `expired`：已无关。

## 研究模式

- `breadth`：广度研究。至少覆盖三条实质不同的路径、方案或视角，横向比较依据、优缺点、适用条件和未知项，形成候选排序，并指出值得转入深度研究的方向。
- `depth`：深度研究。聚焦一个明确对象或路径，追踪证据、源码或实现细节、约束与反例，验证关键结论，并记录置信度、剩余缺口、风险和下一步。
- 广度研究在继续搜索不再产生新的重要类别时停止；深度研究在核心问题已有证据支撑，或阻塞条件已明确记录时停止。
- 新建研究只创建 pending D，不提前生成 W 或 L；pending 和 doing 进入 `agent-brief.json.activeResearch`。
- Agent 领取后改为 doing；短结果直接写回 D，较长结果完成后才创建关联 W；完成后改为 done，并只写一条 L 工作记录。
- 运行时不自动迁移旧字段；旧项目需要迁移时，按[旧项目迁移说明](./旧项目迁移说明.md)单独处理。
- 明确的修改要求、缺陷和执行待办进入任务，不进入研究。

## 写入规则

- 所有项目记录必须包含 `version:: Vxxx`。
- 记录按短 ID 倒序保存，较大的 ID 写在较小 ID 前面。
- 写入通过项目级队列串行化，并使用临时文件原子替换。
- `record-counters.json` 持久保存各类记录的最大编号，删除记录后不复用 ID。
- Markdown 变化后重新生成 `agent-brief.json`、`当前项目基线.md` 和 `index.json`。
- 新记录只写入 `agent-brief.json.currentDataPaths` 指向的当前版本文件。

## 工作记录语义

- 任务保存意图和完成口径：用户原话、执行定义、验收；deep 额外保存深度原因、关键约束、方案与回退。
- 关联任务的 light/standard 日志只保留 `### 结果`、`### 修改文件` 和 `### 验证`。
- deep 日志只在执行中实际形成或改变高影响取舍时增加 `### 关键判断`，完全按任务既定方案执行时省略。
- 使用 `task_short_id:: T000` 的即时 light 日志因为没有任务卡可回查，额外保留 `### 用户目标`。
- 持续风险、验证缺口和后续工作写入独立 `Rxxx`，日志结果只引用编号，不重复正文。
- 文件修改按任务和验收轮次记日志，不按文件数计数；同一轮验收关闭前的相关小修可合并，关闭后的修改新建 Lxxx。
- 任务状态、问题回复、研究状态和自动生成的 brief/index/基线属于协作元数据或派生缓存，不单独触发工作记录，也不递归生成日志。
- Agent 执行前读取任务中的验收，完成情况写入日志结果，实际检查写入验证，不再复制任务内容。
- 新模板不兼容旧字段；旧项目按迁移文档一次性整理，不在解析和展示层长期保留双格式。

## Agent 启动顺序

1. 读取项目根目录的 `.agent-collaboration.md`，定位管理数据目录。
2. 读取 `agent-brief.json`。
3. 读取 `skills/project-collaboration/SKILL.md`，以它作为任务等级、合并和日志格式的唯一完整规则来源。
4. 仅在人类可读概览有帮助时读取 `collaboration/当前项目基线.md`。
5. 默认只读取当前工作相关的 `currentDataPaths` 记录。
6. 需要长期规则时读取 `constraints/项目约束.md`。
7. 只有当前工作相关、上下文不足或用户明确要求时才读取风险、研究、知识和历史版本。

应用启动时会统一刷新所有已登记项目的基线、数据规范、交接说明、SKILL 和派生 JSON；不会借此迁移或补写旧项目的业务 Markdown。

内置 Agent 的运行上下文与协作存储分层处理：模型只接收当前目标、验收、任务约束、有效的用户项目约束、阶段事实和证据；不会把 agent-brief 的导航说明、系统生成的数据规范或日志写入流程重复注入为任务约束。任务状态、版本归属和完成日志由项目适配器统一结算。运行时提示词负责目标锚点、工作等级、阶段动作、动态重规划和证据要求，SKILL 负责外部 Agent 直接操作协作 Markdown 时的完整格式规则。
